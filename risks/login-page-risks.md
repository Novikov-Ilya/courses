# Login Page Security & Functional Risks (Risk Register)

### RISK-01: Server Error Exposure in Client State
\- **Category**: Security / UX Flaw
\- **Description**: The component captures server error messages returned from `await logIn(formData)` directly into the state variable `loginError` and renders them via `{loginError}`. There is no sanitization, truncation, or obfuscation logic applied to this string before rendering. If a vulnerability exists on the backend (e.g., stack traces in production DB errors), these full payloads are leaked directly to the browser DOM without escaping special HTML characters.
\- **Impact & Blast Radius**: Information Disclosure; users see internal server architecture details; malicious actors can fingerprint environment versions or database structures via repeated submission with standard payloads. Users also experience a "dead end" UX where they might think their network connection dropped, unable to distinguish between UI bugs and auth failures without technical logs.
\- **Priority**: High (Security Risk) / Medium (UX Impact). Justification: Direct exposure of error messages is an OWASP top-tier vulnerability in authentication flows if unhandled properly.

### RISK-02: Race Condition on Rapid Re-submission
\- **Category**: State Management / Logic Flaw
\- **Description**: The `submitForm` function does not contain any guard flags (e.g., a boolean `isSubmitting`) or disabled state propagation to the `<Button>` element upon clicking. When a user clicks the login button multiple times in rapid succession, React may trigger multiple async calls to `/login-api`. If the backend has rate-limiting logic per IP/token that is stricter than standard limits but lenient on retries from different browsers (or if frontend caching bypasses), this can lead to account lockouts or token spamming. Furthermore, subsequent `navigate('/courses')` redirects will occur sequentially in a stack rather than cancelling previous ones until the navigation chain resolves naturally upon success of one request only (though usually handled by React Router's history state).
\- **Impact & Blast Radius**: Denial of Service (DoS) on specific user sessions; potential rate limit bans for the authenticated session due to client-side retry storms. If server side does not implement robust token handling logic per-session, this might result in duplicate login tokens being issued if backend architecture is naive about concurrency control on auth attempts.
\- **Priority**: Medium / High (Business Impact). Justification: Can lock legitimate users out of their accounts or trigger expensive rate-limit penalties against the application infrastructure.

### RISK-03: Client-side Validation Bypass via Direct Submission
\- **Category**: Logic Flaw
\- **Description**: The form utilizes `noValidate` on `<SimpleFormStyled>`, effectively disabling HTML5 default browser validation (which often intercepts and blocks submission if required fields are missing). While we have custom hooks for error states (`useInputError`), the code does not enforce that the input value exists *before* calling `logIn(formData)` unless explicitly coded inside a guard condition check. The current implementation allows an empty string object `{}` to be passed to `logIn()` if focus is lost rapidly, or in case of asynchronous race conditions between blur logic and manual submit triggers (e.g., keyboard event handling issues).
\- **Impact & Blast Radius**: Users can trigger the API call with invalid/empty data without seeing immediate UI errors. This relies entirely on backend error responses to handle validation failures rather than intercepting at the front-end level, causing unnecessary network traffic for 4xx client errors and latency increases in perceived performance.

### RISK-04: Missing CSRF Token Handling
\- **Category**: Architectural Gap / Security Risk (Implied)
\- **Description**: The `logIn` implementation is abstracted behind a hook from `@hooks`. In modern single-page applications using React Router (`useNavigate`) alongside API calls, there must be an accompanying anti-CSRF mechanism. If this component relies on backend session cookies or tokens for authentication, and the submission endpoint accepts POST requests to `/courses`, ensure no cross-site request forgery protection is in place. Although specific header handling isn't visible here due to abstraction layers (`@hooks`), if `useFormValidate` does not inject CSRF headers into network payloads explicitly before calling the API service inside that hook chain, there remains a risk of state mutation attacks on shared browser sessions or cross-origin attack vectors from malicious embedded sites.
\- **Impact & Blast Radius**: Cross-site request forgery (CSRF) allows attackers to force authenticated users into logging in for unauthorized accounts; potentially escalating access levels if the user has admin rights but no anti-CSRF protection is implemented.

### RISK-05: Incorrect Error State Trigger Timing
\- **Category**: UX Flaw / Logic Defect
\- **Description**: The implementation sets `loginError` using a setter (`setLoginError(error)`) immediately after awaiting an error result without resetting the timer or clearing previous errors if multiple requests are pending. If there is any internal buffering issue in `useUser()` hook (e.g., race conditions during network request cancellation), old stale errors might remain displayed longer than intended unless properly managed with a useEffect cleanup function to reset state when unmounting or re-validating. This leads to "stuck" error states where users see past failures indefinitely if they manually clear input fields again after seeing an error message but before the UI resets visually (if manual reset is triggered elsewhere).
\- **Impact & Blast Radius**: Persistent display of outdated messages confuses legitimate users; could mask new errors with old ones due to improper state management cycle handling or asynchronous sequencing conflicts between hooks.

### RISK-06: Lack of Input Length Sanitization Logic in Hook Calls
\- **Category**: Security / State Management Flaw (Implied)
\- **Description**: The `useInputHandler` hook receives default values (`formFieldsInitValue`) but lacks visible evidence that input sanitization occurs before passing to API calls. Since we see raw strings passed directly via `<input ... value={formData.email} />`, malicious script injection characters like `"javascript:alert(1)"` could be sent without explicit trimming/sanitizing inside `onChange`. Even if the backend validates this, relying on client-side trust for input boundaries is a flawed assumption; users should never be able to pass executable scripts via inputs intended solely for text fields.
\- **Impact & Blast Radius**: XSS Vector propagation potential depending on how `logIn()` processes and stores sensitive user data (tokens) based on unfiltered raw strings; injection attacks possible if frontend fails to sanitize before passing payload up the chain.

### RISK-07: Missing Focus Management Cleanup Logic
\- **Category**: State Management / Architectural Flaw
\- **Description**: The component does not define any cleanup logic or `useEffect` hook for handling unmounting scenarios when transitioning away from login routes while typing (`onBlur`). While React's lifecycle naturally cleans up refs, there is no explicit guard clause to reset focus states if an error occurs during routing transition (e.g., rapid tab switching). Without explicit state resets in the component destructor pattern or dependency array logic, users might experience flickering input values or persistent blur events triggering unnecessary validation cycles on new routes.
\- **Impact & Blast Radius**: Minor UX degradation; potential memory leak over time if event listeners (`onBlur`) are not cleaned up when components unmount due to missing dependencies in effect scopes (though unlikely given standard React practices, this represents a gap in documented cleanup strategy).

### RISK-08: Missing Explicit Navigation Guard for Authenticated State
\- **Category**: Logical Architecture / UX Flow Gap
\- **Description**: While the code navigates users away from login upon success (`navigate('/courses')`), it does not explicitly redirect if an existing authenticated session already exists (via `useUser` hook check logic potentially inside hidden guards). If a user manually refreshes or hits back button after logging in elsewhere, they may be stuck on this page instead of being redirected to `/dashboard`. The current flow implies reliance solely on API success response rather than checking auth state upfront before attempting login entirely—leading to potential wasted requests if users try logging into an already authenticated account.
\- **Impact & Blast Radius**: Sub-optimal user experience where valid sessions cannot auto-resume; unnecessary re-authentication attempts wasting server resources and increasing latency for returning logged-in users who might expect a seamless redirect instead of repeated API calls due to stale session checks missing in UI layer logic flow definition.
